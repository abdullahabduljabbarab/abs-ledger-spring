# Architecture Decision Records

## ADR-001: PostgreSQL for development, tests and target

One database engine everywhere. The concurrency protection relies on PostgreSQL
row-level locking (`SELECT ... FOR UPDATE`) and the append-only guard is a
PostgreSQL trigger, so the tests must run against real PostgreSQL, not an
in-memory substitute like H2 whose locking and DDL differ. Testcontainers gives
each test run a throwaway PostgreSQL so CI exercises the same engine as a
deployment would.

## ADR-002: BigDecimal over double

All monetary values use `BigDecimal` and `numeric(19,2)`. Floating-point
arithmetic accumulates rounding error over repeated operations. For financial
software this is a correctness requirement, not a preference, and it is the first
thing a banking reviewer checks.

## ADR-003: Append-only ledger, enforced in the database

Entries are never updated or deleted; corrections are compensating entries. This
is enforced three ways: no setters on the entity, no mutating endpoint, and a
trigger that raises on any `UPDATE` or `DELETE` of `ledger_entries`. The trigger
means the guarantee holds even against a direct SQL statement, not only against
the application.

## ADR-004: Spring Boot (Web + Data JPA)

The stack a bank actually runs. Spring Web for the REST surface, Spring Data JPA
over Hibernate for persistence, Bean Validation for request checking, springdoc
for OpenAPI. It keeps the controller, service and repository layers cleanly
separated, which is the structure the invariants live in.

## ADR-005: Pessimistic row locking with deterministic order

Accounts are locked with a pessimistic write lock before a balance check, so two
concurrent withdrawals cannot both read a sufficient balance and overspend.
Transfers lock both accounts in ascending id order, so opposing transfers between
the same pair take the locks in the same order and cannot deadlock. Optimistic
locking was rejected because the contended path is a balance check, where a retry
storm under load is worse than a short wait.

## ADR-006: External Clearing account

Deposits and withdrawals balance against an internal system account, so cash
entering or leaving the system still obeys double-entry. Single-sided entries for
deposits and withdrawals were rejected because they would break the global
zero-sum invariant. The account is seeded by the migration with a fixed id, which
also removes the cold-start race on first use.

## ADR-007: Request hashing, and 200 versus 201

An idempotency key is stored with a SHA-256 hash of the canonical request. Same
key with the same hash is a safe retry and returns the original transaction with
**200**; same key with a different hash is a **409 Conflict**. Returning 200 for
a replay and 201 only for a genuinely new posting makes a duplicate request
visibly not a second posting.

## ADR-008: Flyway owns the schema, Hibernate validates

Schema changes are versioned Flyway migrations, not generated by Hibernate.
Hibernate runs in `validate` mode so a mismatch between the entity mapping and the
migrated schema fails at startup. This keeps the database, not the ORM, as the
source of truth for the constraints the service depends on.

## ADR-009: Constraints in the database, not only in Java

Positive amounts (`CHECK`), a single-use idempotency key (`UNIQUE`), entries that
reference a real transaction and account (`FOREIGN KEY`), balanced transactions (a
deferred constraint trigger that rejects a non-zero-sum transaction at commit), and
immutable entries (trigger) are all declared in the migration. The zero-sum rule is
a cross-row invariant, so it needs the deferred trigger rather than a plain
constraint; a foreign key alone proves referential integrity, not balancing. The
Java `@Transactional` logic then enforces what PostgreSQL already refuses, so a bad
write is rejected even if the application logic were wrong.
